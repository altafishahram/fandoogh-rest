# امنیت REST و کنترل دسترسی در وردپرس

این مهارت برای ساخت یا بازبینی هر endpoint جدید در `includes/FrontendDashboard/RestApiController.php` و هر جای دیگری که دادهٔ رستوران را تغییر می‌دهد استفاده می‌شود.

## ۱. مجوز باید مختص هر عمل باشد، نه یک Boolean

الگوی غلط: یک `check_permission()` مشترک که فقط «عضو یکی از نقش‌ها بودن» را بررسی می‌کند و روی همهٔ routeها تکرار می‌شود.

الگوی درست:

- برای هر route یک `permission_callback` مستقل یا یک آرگومان `capability` در ثبت route تعیین کن.
- ماتریس نقش/مسیر را صریح بنویس و در همان فایل به‌روز نگه دار.

| عمل | capability پیشنهادی | نقش‌های مجاز |
|---|---|---|
| خواندن منو و سفارش‌های شعبهٔ خود | `view_kitchen_orders` | آشپزخانه، مدیر شعبه |
| تغییر وضعیت سفارش | `edit_kitchen_orders` | آشپزخانه، مدیر شعبه |
| ویرایش قیمت/موجودی شعبه | `manage_branch_inventory` | مدیر شعبه |
| ایجاد/حذف محصول و دسته | `manage_restaurant_menu` | مدیر رستوران، مدیر کل |
| آپلود رسانه | `upload_files` + بررسی نوع فایل | مدیر رستوران، مدیر کل |
| تغییر تنظیمات افزونه | `manage_options` | مدیر کل |

قاعده: هر نقش فقط حداقلِ لازم را دارد. نقش آشپزخانه هرگز نباید حذف محصول یا آپلود فایل داشته باشد.

## ۲. محدودسازی شعبه را در سرور اعمال کن

- شناسهٔ شعبه‌ای که از کلاینت می‌آید «ادعا» است، نه مجوز.
- یک guard مرکزی بساز (مثلاً `BranchAccessPolicy::assert_branch($branch_id)`):
  - کاربر مدیر کل/فروشگاه: همهٔ شعب.
  - بقیه: فقط شعبه‌هایی که در `AuthController::get_user_branches()` برمی‌گردند؛ در غیر این صورت خطای 403.
- برای منابعی که خودشان شعبه دارند (سفارش، رسید، محصول شعبه‌ای) مالکیت را از روی خود رکورد بررسی کن، نه فقط پارامتر ورودی.
- در کوئری‌ها فیلتر شعبه را در همان query اعمال کن؛ فیلتر بعد از واکشی، نشت داده است.

## ۳. تغییر جزئی، نه بازنویسی رکورد

هر عملیات «فقط یک فیلد را عوض کن» باید همان ستون را با `$wpdb->update()` تغییر دهد. `INSERT ... ON DUPLICATE KEY UPDATE` با مقادیر پیش‌فرض برای فیلدهای ارسال‌نشده، دادهٔ موجود را پاک می‌کند.

- `toggle_stock` → فقط `stock_status`, `is_available`
- `update_price` → فقط `regular_price`, `sale_price`
- قبل از هر upsert، اگر رکورد وجود دارد، مقادیر فعلی را merge کن.

## ۴. ورودی، خروجی و اثر جانبی

- هر پارامتر را با `absint`، `sanitize_text_field`، `floatval` یا schema خودِ `register_rest_route` اعتبارسنجی کن.
- GET باید بدون اثر جانبی باشد؛ تغییر کوکی، وضعیت یا دیتابیس فقط با POST و همراه nonce یا بررسی `X-WP-Nonce`.
- کوکی‌های نشست/شعبه: `HttpOnly=true`، `SameSite=Lax`، و `Secure` روی HTTPS.
- آپلود فایل: محدودیت MIME، اندازه و capability؛ هرگز به پسوند اکتفا نکن.
- کلید سرویس‌های خارجی (مثل مترجم) را در پاسخ API، لاگ یا خروجی خطا نمایش نده؛ پاسخ خطای سرویس را پاکسازی کن.

## ۵. چک‌لیست بازبینی

- [ ] هر route یک مجوز مشخص دارد و ماتریس نقش/مسیر مستند است.
- [ ] شعبه در همهٔ مسیرهای نوشتن اعتبارسنجی می‌شود.
- [ ] مسیرهای GET بدون اثر جانبی‌اند.
- [ ] به‌روزرسانی‌ها جزئی‌اند و فیلدهای دیگر را خالی نمی‌کنند.
- [ ] خروجی خطا دادهٔ حساس برنمی‌گرداند.
- [ ] برای هر سناریو یک تست بازتولید (نقش محدود + شعبهٔ غیرمجاز) وجود دارد.
